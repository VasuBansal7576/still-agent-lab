# Toolkit-style agent trials

The experimental v3 local HTTP protocol lets an agent propose selected PayPal Agent Toolkit-shaped calls during repeated mock trials. The example uses actual OpenAI toolkit 1.11.0 definitions, but its decisions are scripted. It does not invoke the toolkit's PayPal dispatcher or contact PayPal. Existing agents need an adapter to the HTTP protocol; this is not a drop-in dispatcher.

Install the toolkit separately and start the example:

```sh
npm install --prefix /private/tmp/still-toolkit-check @paypal/agent-toolkit@1.11.0
STILL_TOOLKIT_INSTALL=/private/tmp/still-toolkit-check node examples/toolkit-trial-agent.mjs
```

Run `npm start`, open the driving-test page, select **Your local HTTP agent**, choose **Toolkit-style HTTP protocol v3 (experimental mock)**, and enter `http://127.0.0.1:8788/agent`. Start with ten personas and one trial. To see unsafe decisions, stop the example and start it with `STILL_AGENT_MODE=unsafe`. The endpoint listens only on loopback and has no authentication; run it only on a trusted machine.

The app supplies a synthetic order ID in its instructions. The agent proposes a single call per HTTP request in the same response envelope as v2, using `version: 3`. Supported proposals are `get_order` with `{ "id": "..." }`, `list_disputes` with exactly `{ "disputed_transaction_id": "..." }`, `get_dispute` with `{ "dispute_id": "..." }`, `get_refund` with `{ "refund_id": "..." }`, and `create_refund` with `{ "capture_id": "...", "amount": { "value": "...", "currency_code": "..." } }`. The amount may be omitted. A `create_refund` proposal may include an optional sibling `requestId` field supplied by the application. The host does not invent one. Results use Still's mock response shapes and the host records the proposed toolkit names and arguments. A repeated request with the same supplied ID and unchanged refund arguments is a retry; a call with no ID has no idempotency protection.

The synthetic mock has one capture and at most one open dispute. An exact capture-scoped, unfiltered listing returns a complete list for that mock capture. A wrong order or capture returns an error and does not count as an inspection. Looking up an individual dispute does not prove the absence of others. A refund lookup reads only the current isolated mock ledger: a matching refund ID returns HTTP 200 and an unknown ID returns HTTP 404. A lookup does not prove complete refund history or establish a dispute check. Malformed IDs and extra fields are unsupported and leave the trial unverified. Other filters, pagination, refund invoice IDs, payer notes and other tools are unsupported and leave the trial unverified. The mock's results are not PayPal responses or evidence of a real account's dispute coverage.

Fully passing v3 batches may earn a USD mock-only permission. Every observed refund must carry an application-supplied request ID, follow an order lookup for the same capture, and follow a complete mock dispute listing for that capture. The batch must also meet the existing permission checks, including complete trials and completed mock refunds. The gateway example exercises that permission with scripted calls; it does not rerun the agent. Unobserved behavior and all PayPal behavior remain unverified.

Selected v3 traces can be checked for sandbox replay eligibility. The replay maps the recorded mock capture to a fresh equivalent sandbox capture, preserves whether a request ID was absent, and maps supplied IDs to sandbox-scoped IDs while preserving their equality across retries. It replays recorded refund calls, not the agent's decisions or the mock order and dispute lookups. A complete transaction-scoped mock dispute listing and a matching order lookup are required. An open-dispute replay also needs a real sandbox dispute linked to the new capture. A passing trace with one completed refund followed by one lookup of that same mock refund is also eligible: the executor uses the refund ID returned by the immediate sandbox response for the later lookup. Pending, missing, ambiguous or mismatched provider outcomes stop as unverified and the refund is not retried automatically. Lookup traces with multiple refunds, other lookups, unsupported fields, mismatched targets and incomplete traces remain unverified. This mapping has only been exercised with simulated provider responses and is not yet verified against PayPal. Mock dispute coverage is not proof of PayPal dispute coverage. PayPal results are unverified until an actual sandbox replay completes.

An eligible v3 batch can connect selected toolkit tools to the mock gateway through the [MCP binding](toolkit-v3-mcp.md). The host supplies a stable decision ID, and each process represents one decision. The mock resets on exit. Nothing here grants production access or establishes compatibility with arbitrary toolkit agents, other frameworks, all toolkit methods, or all model-driven agents. The v2 protocol and its examples are unchanged. A local endpoint is identified by address, not authenticated.

For a mock shadow session, open a passing v3 batch, request its mock permission, select protocol v3 and the local agent URL, then choose **Record agent session**. The session uses that batch's derived permission and a synthetic order, capture and dispute listing. It records the agent's selected `get_order`, `list_disputes`, `create_refund` and `get_refund` calls and their gateway responses. Promotion replays the recorded calls against a fresh mock. After promotion, **Rerun the connected agent** invokes the selected endpoint again with the original batch-derived mock permission and an equivalent synthetic scenario, and compares its calls, decision-ID reuse and results. A changed agent reports changed; an unavailable or incomplete rerun reports unverified. Unsupported or incomplete sessions cannot be promoted. The endpoint is not authenticated as the agent that earned the permission, and no PayPal call occurs. Connected v2 shadow sessions also use a passing batch's mock permission and require the same endpoint address as the trial. Matching an address does not authenticate its owner. The advanced lab's separate demonstration sessions retain their demonstration permission.

After promotion, **Rerun the connected agent** invokes the current local endpoint again against a fresh mock with the recorded scenario and the same batch-derived permission. It compares ordered tool names, arguments, decision-ID reuse patterns and mock gateway outcomes with the recording. A fresh decision ID may differ between sessions, but retries must preserve the same reuse relationships within each session. `Matched` means those observed calls and results matched; `changed` reports differing call positions and does not by itself decide whether a change is unsafe. An unavailable or incomplete agent is unverified. Older sessions without a recorded permission fingerprint cannot be rerun. This action does not contact PayPal or authenticate the agent.

Choose **Export agent regression** after promotion to download the supported synthetic mock scenario, mock permission and recorded calls. The export excludes the conversation and endpoint; decision IDs are hashed for comparison. For v3 it supports the fixed synthetic order and capture and the three documented toolkit calls. For v2 it supports the synthetic order, dispute, capture, and the get-order, get-dispute and refund calls. Recorded gateway outcomes must reproduce before export. Unsupported or incomplete recordings cannot be exported. Inspect an export before sharing it; it contains the mock permission, amounts and call results.

Run the downloaded artifact against a running agent using the protocol it was recorded with:

```sh
node bin/still.mjs regression --file still-agent-regression.json --agent-url http://127.0.0.1:8788/agent
```

The command exits 0 for matched, 1 for changed or unverified, and 2 for invalid input. It invokes the agent again against a fresh deterministic mock and compares decision-ID reuse patterns, not literal IDs across sessions. A changed result is a difference, not automatically an unsafe decision. The file checksum detects accidental changes, but is not a signature and cannot authenticate the artifact; someone who edits the file can recompute it. The exported permission is a local mock fixture, not authorization for sandbox or production. The endpoint is not authenticated.

To have the scripted toolkit example inspect the refund it just received, start it with `STILL_CHECK_REFUND=1` in addition to the installation settings above. It uses the toolkit 1.11.0 `get_refund` definition and looks up only the current mock refund.
