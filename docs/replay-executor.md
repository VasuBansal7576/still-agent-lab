# Sandbox replay executor

`executeSandboxReplay` in `server/replay-executor.mjs` executes one ready item from `planSandboxReplays`. Pass its receipt in the `evidence` array to `reconcileSandboxReplays`. It supports one explicit, confirmed mock refund on a completed capture with a clear mock dispute state. Other traces remain unverified. It does not create orders, approve payments, or capture payments.

The trusted server-side caller must bind `sessionId` and `adapter` to the same PayPal sandbox account. The caller supplies `approval` with `sessionId`, `captureId`, and `humanApprovedFreshCapture: true` after a human approves that fresh capture for this use. The caller also supplies `refundHistory` with the same session and capture IDs, `complete: true`, `refundedAmount: '0.00'`, currency, source, and an ISO `observedAt`. This is a trusted attestation based on complete provider evidence, not a value inferred from the capture status. The caller must keep the capture exclusive to this replay between that observation and the refund. An unrelated actor can otherwise refund it during that interval. If the caller cannot establish that evidence, do not execute the replay. The current PayPal adapter does not supply a complete per-capture refund history.

The executor reads the capture and checks its ID, status, amount, and currency before refunding. The caller must provide `reserve({ sessionId, captureId, key, requestId })`, an atomic durable operation that returns true only when it records a first reservation for both the capture and the replay key. It must reject reuse across concurrent calls and process restarts. A reservation is never released automatically, including after errors or an uncertain response. The caller must investigate provider state before any manual recovery. Request IDs are deterministic for the session, capture, and replay key.

The executor saves only selected provider fields, issue codes, and an error stage and type. It does not save error messages, credentials, authorization headers, or provider descriptions. An exception during refund leaves the outcome uncertain. A completed refund has status `completed`. A 4xx response with a named error and issue has status `rejected`. Other responses remain unverified and retain sanitized response fields. No automatic retry occurs. A simulated adapter must set `simulated: true`; its results cannot contribute to the live agreement score. Only trusted callers may invoke this module. It exposes no HTTP endpoint and does not itself verify the provenance of the adapter or attestations. The caller must record the receipt in a protected execution ledger and provide a server-owned verifier to reconciliation. No such integration exists yet.
