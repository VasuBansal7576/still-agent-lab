# Sandbox replay and refund history

PayPal's [capture details endpoint](https://developer.paypal.com/api/payments/v2/captures-get/) returns a capture by ID, and its [refund details endpoint](https://developer.paypal.com/api/payments/v2/refunds-get/) returns a refund by known ID. Neither establishes a complete, current list of refund attempts. [Transaction Search](https://developer.paypal.com/community/blog/PayPal_AG_Grid_Part_1/) can lag, so an empty report does not establish that no refund is pending.

For sandbox-only comparisons, Still creates an order for the selected replay, observes buyer approval, captures it, and checks that PayPal reports a matching `COMPLETED` capture. A durable reservation permits Still to use that capture and replay key at most once. Each receipt explicitly records that complete refund history is not established. An external or pending refund can exist even when the capture appears completed; the comparison records the actual PayPal response and must not imply exclusive account access or a production safety guarantee. An uncertain outcome is not retried automatically.

This sandbox comparison is not a live-account refund permission. A production implementation needs a trusted system that records every refund decision and uncertain outcome from capture creation onward, accounts for external refund paths, and reconciles provider evidence. It must fail closed after gaps or uncertain outcomes and prevent concurrent refund decisions.
