# Multi-call sandbox reconciliation

The original 5,000-failure batch had 807 authenticated sandbox receipts with fewer provider refund responses than recorded mock calls. Earlier work created 769 one-use delayed continuation journals. A further guarded pass found 31 eligible first `PENDING` refunds without a continuation journal and sent each recorded second decision once. All 31 produced comparable PayPal sandbox responses and disagreed with the completed-refund mock. Across both passes, the saved ledger has 800 delayed journals: 799 comparable disagreements and one unverified HTTP 503. Delayed calls occurred after the original mock and do not replace the original immediate score.

The other seven original receipts recorded a definitive HTTP 422 on their first sandbox refund call. Still made a separately reserved fresh sandbox capture and replay for each, leaving every original receipt unchanged. Two fresh replacements produced both recorded refund responses: each PayPal response was HTTP 201 `PENDING` with a distinct refund ID, and each full trace disagreed with the mock. PayPal returned HTTP 422 `REFUND_FAILED_INSUFFICIENT_FUNDS` on the first call for the other five fresh captures. The executor stopped after the rejection; those five full traces remain unverified. A rejection is not proof of a second refund action or of a completed refund.

[Sanitized evidence](evidence/multicall-reconciliation.json) includes the seven separate replacement batches and their real sandbox capture and refund responses. The original 5,000-trial batch shows the fresh replacements separately. Complete external refund history and exclusive access are not established.

To run a guarded fresh replay of an eligible original trial, use `node server/fresh-rejected-replay.mjs BATCH-ID PERSONA-ID TRIAL`. The command requires an authenticated original one-call receipt with a supported definitive 422, a two-decision non-dispute mock trace, and a one-use reservation. It creates a fresh sandbox capture, never retries an uncertain provider response, and leaves the original receipt unchanged. The existing `server/pending-continuation-queue.mjs` handles eligible confirmed pending first refunds and retains a distinct delayed journal.

The command authenticates before creating its replay reservation. By default it uses the connected sandbox account in Keychain. For an isolated sandbox merchant, supply `PAYPAL_CLIENT_ID` and `PAYPAL_CLIENT_SECRET` privately in the process environment and set `STILL_REPLAY_USE_ENV_CREDENTIALS=1`. Do not put secrets in command arguments, files, logs or saved evidence. The original Keychain connection is not replaced. A new merchant's replacement is labeled separately and cannot establish the outcome of the earlier merchant's call. The isolated path has been checked with rejected credentials; a successful run with a separate merchant is still unverified.
