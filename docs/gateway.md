# Gateway integration

The gateway is an experimental in-process boundary. It does not bind to PayPal, create credentials, or connect to an account. The stdio executable starts unbound and rejects refunds. It supports only the toolkit's `get_order`, `get_refund`, `get_dispute`, and `create_refund` tools. It is not a complete drop-in replacement for the PayPal toolkit.

The tool names and refund parameters come from PayPal's [tool registry](https://github.com/paypal/agent-toolkit/blob/main/typescript/src/shared/tools.ts) and [TypeScript parameter definitions](https://github.com/paypal/agent-toolkit/blob/main/typescript/src/shared/parameters.ts). `create_refund` takes `capture_id`, optional `amount: {value, currency_code}`, `invoice_id`, and `note_to_payer`. Still deliberately blocks requests with no amount and currently blocks `invoice_id` and `note_to_payer`. The toolkit's older PROMPTS.md describes a different amount shape, so the source definition takes precedence.

Run `node examples/toolkit-client.mjs` to see MCP initialize, tool discovery, and a denied refund over stdio. Run `node examples/toolkit-client.mjs --demo` to connect to a disposable mock and earn a $50 mock grant from a passing trial. The client requests $60, which the grant blocks, then refunds $50 and replays that decision. The two successful replies have the same mock refund ID. Neither command calls PayPal.

An MCP host can start `node /absolute/path/to/server/toolkit-mcp.mjs --demo` to use the same disposable mock binding. Its capture ID is `MOCK-CAPTURE-toolkit`. This binding uses one fixed decision ID, so it is limited to one refund decision per process. Start without `--demo` for the unbound, fail-closed process. A host integration can import `createMcpHandler` and inject a gateway, a session ID and a stable decision ID. The host must bind each distinct refund decision to a different ID and reuse that ID on retries. The executable does not yet bind an external account or select distinct decision IDs.

`derivePermission({agentId, currency, summary})` accepts a trusted batch from `runTrials`. It requires the batch's `evaluatedAgentId` to match the requested agent, every expected persona and trial to be present and passing, and at least one completed mock refund visible in both the trace and the final mock ledger. Its ceiling is the largest observed completed refund in that currency. The resulting grant is scoped to `deterministic-mock`, identifies the number of trials, and labels sandbox replay and unobserved coverage as unverified. It does not assert that the agent passed every possible policy scenario or grant live or sandbox refund authority. Missing, duplicate, failing or ambiguous evidence denies the grant. Treat batch output and agent binding as trusted host data; JSON fields cannot authenticate themselves.

A host constructs `createGateway({agentId, permission, adapter, mode})`. A mock grant can execute only on a host-bound adapter declaring `trusted: true`, `replaySafe: true` and `stableRequestIds: true`. These declarations must describe an isolated mock that forwards the request ID and implements stable idempotency; they are not proof of sandbox behavior. No live or sandbox adapter can use a mock grant. `mode` is `enforce` or `shadow`; both enforce the same guard and record calls. `adapter.inspect(captureId)` must return current authoritative `{captureId, paymentStatus: "COMPLETED", currency, disputeState: "CLEAR", identityMatches: true, cancellationComplete: false, remaining, approvedAmount, refundedToDate}`. Monetary fields are decimal strings. `approvedAmount` is the remaining amount approved for this decision, and `refundedToDate` is the total already refunded on the order. Missing or uncertain facts block the call. `adapter.refund(captureId, {amount, currency, requestId})` must forward the request ID as PayPal-Request-Id and return `{ok, status, body}`. Optional `get_order`, `get_refund`, and `get_dispute` methods accept an ID and return the same response shape. The host is responsible for binding the adapter to the intended account and providing trustworthy, current identity, approval, order, dispute, and refund information. The existing sandbox adapter alone does not supply these facts.

Call `gateway.call({sessionId, decisionId, name, arguments})`. The gateway serializes refund calls within one process and derives an idempotency key from the agent and decision. It blocks reuse of a decision ID with changed arguments in that process and returns a cached completed response for an identical decision replay. Unknown outcomes require reconciliation. Enforcement cannot protect calls that bypass this gateway, changes made concurrently outside it, or multiple gateway processes. Its in-memory decisions and sessions do not survive restarts. It is not ready for production payment authority.

`gateway.events(sessionId)` returns recorded tool events. `gateway.promote(sessionId)` creates a regression containing the recorded calls. `gateway.replay(regression)` runs them only against an adapter explicitly marked `replaySafe: true`; use a resettable mock, never a live account. Promotion captures tool inputs, not the customer's conversation or an agent's decision-making, so replay exercises the gateway rather than rerunning the original agent. The driving-test page provides a mock shadow-session store and one-click promotion. See [shadow sessions](shadow-sessions.md). Events use a constrained response shape, but IDs and amounts are still sensitive; protect saved sessions and avoid including secrets in IDs or free-text fields.

For a host-selected passing batch, use the [batch MCP binding](mcp-batch-binding.md). It does not authenticate the connecting client. The mock gateway requires a matching successful `get_dispute` call before a refund.
