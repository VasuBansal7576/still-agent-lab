# Sandbox account personas

`importSandboxAccountPersonas({ paypal, startDate, endDate, count, seed })` in `server/account-personas.mjs` reads the connected sandbox account using a client from `createPayPalSandbox`. Dates are ISO timestamps spanning at most 31 days. `count` defaults to the number of usable positive transaction records, and may be up to 100,000. The return value contains `personas`, `evidence`, `importedTransactions`, and `importedDisputes`. The driving-test page calls this importer for the connected sandbox account and displays the evidence and example personas.

The importer calls only sandbox GET endpoints for the transaction report, dispute list, and dispute details. It does not create disputes or use the live PayPal endpoint. Enable the relevant reporting and Disputes features and permissions for the sandbox app. PayPal documents the reporting scope as `https://uri.paypal.com/services/reporting/search/read` and list-disputes scope as `https://uri.paypal.com/services/disputes/read-buyer`. Access can still be denied, reports can lag by up to three hours, and account data may be empty. Each retrieval has an explicit status and reason; missing results do not establish that no transactions or disputes exist. Reports are capped at 100 pages. Incomplete, malformed, or changing report pagination produces no personas. A dispute listing with a next page is marked incomplete, and individual detail failures are also incomplete.

Each usable transaction supplies a source ID and amount. `accountEvidence.transaction` also records the report page, row, and initiation time when available. PayPal notes that transaction IDs are not necessarily unique in reporting; an ID alone does not identify a unique report row. Page and row identify the returned row within this import, not a permanent PayPal identifier. An order ID is included only when PayPal explicitly marks the reference as an order. Related report rows are included only when they explicitly reference the seed transaction ID, and each includes its own page and row. Because an ID can occur in multiple rows, a reference does not establish which row it refers to. Report events T1107 and T1120 are labeled as payment refund events and excluded as scenario seeds. This classification is from the report, not a separate refund API response or proof that a refund completed. Other related events are not assumed to be refunds. A dispute is linked only when its detail explicitly identifies the same seller transaction ID; its reported amount and status are retained when valid. Raw responses, names, email addresses and other customer details are not retained. The account-derived source IDs are still account data and should be protected accordingly.

The persona generator makes fictional customer requests, customer and order identifiers, return approvals and dispute states. The synthetic approved amount is half the reported amount and is not an actual approval. Scenario mutations may posit a dispute even when none was observed. `accountEvidence` separates retrieved facts from these assumptions, and lack of a linked dispute is unverified. These scenarios are not real customers, and an imported record does not prove that its transaction is a captured payment eligible for refund. Sandbox execution must establish its own fresh payment evidence.

PayPal references: [Transaction Search API](https://developer.paypal.com/api/transaction-search/v1/), [transaction fields](https://developer.paypal.com/api/transaction-search/v1/definitions/transaction_detail/), [transaction event codes](https://developer.paypal.com/docs/transaction-search/transaction-event-codes/), and [Disputes API setup and access](https://developer.paypal.com/platforms/disputes/integrate-disputes/).
