# Driving test upgrade: acceptance evidence

Updated 2026-11-11. The upgrade is incomplete. Sandbox evidence below is distinct from the deterministic mock; neither synthetic personas nor these trials establish real-world failure rates.

| Acceptance | Status | Evidence and limits |
| --- | --- | --- |
| $100 retry leak and stable request ID against PayPal | Passed in sandbox | [Sanitized evidence](evidence/sandbox-retry.json) records two distinct HTTP 201 $50 refunds on one $100 capture for the buggy run. The fixed run uses the same request ID and receives HTTP 201 then HTTP 200 for the same refund ID. PayPal subsequently reported the buggy capture as refunded and the fixed capture as partially refunded. The agent timeout was injected, not an actual network failure. |
| Other refund leaks | Passed in sandbox with synthetic policy facts | [Four recorded cases](evidence/sandbox-extra-leaks.json) show PayPal HTTP 201 and completed refunds: an omitted amount refunded the full $100; an explicit $100 exceeded a synthetic $50 approval; wrong-order and wrong-customer scenarios refunded $50 each despite synthetic mismatches. PayPal re-reads confirmed the first two captures `REFUNDED` and the others `PARTIALLY_REFUNDED`. Identity and approved-return facts are synthetic, not verified customer records. |
| Open dispute rule with a real sandbox dispute | Passed in sandbox | [Sanitized evidence](evidence/sandbox-dispute.json) shows PayPal returned HTTP 201 for a $50 refund while the linked dispute was `UNDER_REVIEW`. Still flagged the refund attempt. PayPal subsequently reported the capture as refunded, the refund as completed, and the dispute as still under review. A dispute payout is not established. |
| 1,000 public-data persona variants and repeated trials | Passed in mock | The driving-test browser ran 1,000 personas × 5 trials for each scripted agent. The generator cites 2,022 public records. The first 1,000 personas cite 1,000 distinct records, including 996 UCI invoices, two τ-bench tasks, one CFPB complaint, and one public discussion. Browser batch `446f8ec5-570f-46e3-818b-022f50080730` completed 5,000 scripted mock trials with this pool. Personas and behaviors are synthetic. |
| Reliability and failure map | Passed in mock | CLI and browser show pass@1, pass^5, and failure clusters. `still test --personas 1000 --trials 5` gave 5,000 passes; `--agent buggy` gave 5,000 failures across duplicate, dispute, identity, missing amount, and approved-return clusters. Scripted trials are deterministic. Browser batch `8f2c48ed-71f6-4e32-aa2f-3d6f6d473d64` used gpt-6.1-terra for one passing mock trial. An earlier model trial was unverified for an unknown reason. The local HTTP example ran 5,000 trials before and after an identity-rule fix: batches `6e98cf87-0b81-45ec-b929-71a3726e6efb` and `9f82c08f-dd0f-4edd-acd6-16adda008cbf` showed 575 failures and zero failures respectively. |
| Real sandbox replays and agreement | Partial | The browser planned ten sampled passes for batch `d0c88817-eae0-471a-93d1-571fdd77f8ca` and replayed two against PayPal sandbox. Both agreed on HTTP status and completed refund amount and currency; [receipts and final states](evidence/sandbox-sampled-replays.json) show USD 87.62 and GBP 319.20 refunds. Eight planned samples remain unverified. A separate failing approved-return trial was replayed against PayPal; its [receipt and final state](evidence/sandbox-failure-replay.json) show HTTP 201 and a completed USD 179.86 refund against a synthetic USD 89.93 approval. The failure map comparison agreed. A timeout-retry failure and an open-dispute failure were also replayed from batch `40f79126-1d0a-4152-b23d-5ef9c221e7ce`; [receipts and final state](evidence/sandbox-failure-replays-more.json) show two GBP 65.40 refunds, and a GBP 139.87 refund while dispute `PP-R-BNM-10199010` was open. The timeout was injected, and a dispute payout is not established. The other failures remain unverified. The queue can be paged through all 5,000 failures; each requires a fresh approved sandbox capture, and each open-dispute case also requires a linked real sandbox dispute. Complete refund history and exclusive access are not established; this is a sandbox-only comparison. See [refund-history](refund-history.md). |

Earlier $50 sandbox traces show an already-refunded capture being rejected with HTTP 422 and the corrected scripted flow avoiding the duplicate. They are not evidence for two successful partial refunds.

The browser generated an AI explanation for failed mock batch `e03272cb-17ea-4459-8435-e992b9179c3e` and cited the refund call and response. The deterministic failure verdict was unchanged. The browser also attempted replay preflight for batch `c6aeb977-fc0e-438f-bdaa-3ef53ee08239`; it reported that no sandbox account was connected and made no replay.

Browser batch `40f79126-1d0a-4152-b23d-5ef9c221e7ce` ran the buggy agent on the expanded persona pool. All 5,000 mock trials failed. A matching checkout request for batch `b6223095-0771-4538-9234-fe2efd908e8f` stopped because the browser session had no PayPal connection.

The existing STILL Sandbox app was reconnected on November 11, 2026. PayPal authenticated the saved credentials and created a sandbox order after a fresh server restart. The payment amount is simulated and no real money moves. The two sandbox captures were approved through the test buyer.

The two sampled replay approvals were performed through the sandbox buyer account by the operator agent. Earlier receipts called the checkout `humanApprovedFreshCapture`; that historical field established buyer approval, not the identity of the operator. New receipts use `buyerApprovedFreshCapture`.
